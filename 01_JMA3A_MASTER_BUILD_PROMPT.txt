- Moroccan
- modern
- premium
- social
- adult enough to be used by university students and adults
- simple enough for casual players
- fast
- reliable
- mobile-first
- install-free

- childish
- cartoonish

======================================================================
2. PRIMARY PRODUCT PRINCIPLES
======================================================================

P1 — REAL-LIFE SOCIAL INTERACTION IS THE PRODUCT
The app coordinates the game. People interact physically.

P2 — INSTANT PLAY
Basic play requires no account, email, phone number, or app-store install.

P3 — ONE PLATFORM, MANY GAMES
Rooms, players, devices, sessions, QR joining, timers, private turns,
reconnect, voting, scoring, localization, content packs, and realtime
transport are PLATFORM capabilities.

Each game plugs into this platform through a clear game contract.

P4 — PLAYER != DEVICE
Multiple players may share one phone.
One player may have their own phone.
A room may mix both.

P5 — SERVER AUTHORITATIVE
Clients express intent.
The server validates and resolves game state.

P6 — PRIVATE DATA IS ACTUALLY PRIVATE
Never send all secrets to every browser and merely hide them in UI/CSS.

P7 — DARIJA FIRST
Moroccan Darija is a first-class product language and content language.

P8 — MOBILE FIRST
Primary target is modern phone browsers at 375px width and above.

P9 — COMMERCIAL-READY WITHOUT MONETIZATION BLOAT
No payments are required in V1, but architecture must not block:
accounts, profiles, achievements, premium content packs, premium games,
cosmetics, statistics, subscriptions, custom rooms, or branded packs.

======================================================================
12. CONCURRENCY / TRANSACTIONS
======================================================================

Multiple players can act at the same time.

Protect against:
- duplicate vote
- duplicate action
- double phase advancement
- double elimination
- stale-state write
- two simultaneous game resolutions
- reusing limited abilities
- repeated submit caused by mobile retries
- reconnect replay

Use:
- DB transactions where appropriate
- unique constraints
- optimistic stateVersion checks and/or row locking
- idempotency keys
- deterministic resolution
- Redis only as coordination/cache/broadcast, not the sole durable truth
  for finished/important game state

Every mutating game command should conceptually operate against:
room/game ID + actor identity + expected state/phase + idempotency key.

======================================================================

14. SECURITY MODEL
======================================================================

SERVER IS AUTHORITATIVE.

Never:
- send all roles to all clients
- send all secret words to all clients
- send all secret missions to all clients
- send Seer results to unauthorized players
- send wolf targets publicly before resolution
- place secrets in HTML and hide them with CSS
- trust client-supplied role/team/status
- let client decide who wins
- let client advance phase without server validation
- let a shared device query arbitrary players' secrets
- embed server secrets in NEXT_PUBLIC_* variables

Every action validates:
- authenticated anonymous session
- room membership
- player identity
- game status
- alive/eligible status where relevant
- current phase
- action permission
- target permission
- limits/cooldowns/consumables
- duplicate submission
- state version / stale request
- payload schema

Add:
- Zod or equivalent validation
- rate limits on create/join/code probing/action spam
- secure headers
- safe error responses
- structured server logs without leaking secrets
- no tokens in logs
- dependency audit hygiene
- CSP where practical
- CSRF-conscious mutation design
- origin checks for websocket connections
- production error boundaries

20. GAME 2 — L'INTRUS
======================================================================

Core social loop:
Most players receive a secret concept/word.
One player is the Intruder or receives meaningfully different information.
Players take turns giving clues verbally.
They must expose enough knowledge to prove they belong without saying the
word directly.
Then players vote for the Intruder.

Required modes:
- MULTI_PHONE
- ONE_PHONE
- HYBRID

Two supported rule variants:
A. NO-WORD INTRUDER
   All normal players receive the same word.
   Intruder receives "You are the Intruder" but no word.

B. CLOSE-WORDS
   Majority receives Word A.
   Minority/Intruder receives closely related Word B.
   Example structure only: "train" vs "tram".
   Actual seed pairs must be original and culturally appropriate.

Quick Game default:
NO-WORD INTRUDER for simplicity.

Flow:
LOBBY
SECRET_ASSIGNMENT
PRIVATE_REVEAL
CLUE_ROUNDS
VOTING
VOTE_RESULT
OPTIONAL_INTRUDER_GUESS
SCORE/RESULT
NEXT_ROUND or GAME_OVER

Rules:
- never reveal word to unauthorized client
- randomize starting player
- show visible turn order publicly
- clue is spoken in real life; no required text entry
- configurable 1–3 clue rounds
- after clues, everyone votes privately
- tied vote: revote tied players
- if Intruder is caught, optional final chance to guess the secret word
- if correct, Intruder may steal/earn win depending settings
- support score-based multi-round session
- play-again preserves group but rerandomizes secrets

Minimum original V1 content:
- at least 120 Darija-friendly secret words
- at least 80 close-word pairs if CLOSE-WORDS variant is enabled
